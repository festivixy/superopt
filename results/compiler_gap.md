# The compiler gap

The compiler gap is a measure of the difference between the number of
instructions emitted in a naive implementation at level -O3 and the formal
minimum demonstrated by a superoptimizer. Starting from three benchmarks, the
set grew to fourteen. This change turned a demonstration into a survey, so this
document's role became different. From fourteen cases, it begins to become
evident what types of naive code are resistant to superoptimization from
contemporary compilers and what types are so susceptible that the main question
changes.

There are no new techniques presented here. The novelty is the measurement
itself: naïve source input gives instruction counts with the superopt column
clearly labeled to demonstrate the extent of formal proof.

## Method

Both sides work on the same naïve source. Superopt reads the Python reference
specification, while GCC and Clang read a line-for-line naïve C translation of
the same specification. The goal is not to feed the compiler with the trick and
observe a simple copy; the goal is to find out whose tool can recognize the
trick in the naïve form, ensuring the equal start from unoptimized state.

This symmetry carries a definition cost: the naïve source should be constrained
enough so the trick and the loop would plausibly diverge. This is exemplified
by the smear_lowest_bit case. The trick x | (x-1) maps zero to all-ones since
0 - 1 wraps to all-ones and the OR preserves it. A naïve loop that searches for
the lowest set bit and fails to find it is not obviously constrained at zero
and might return any value. I chose all-ones both in the Python specification
(superopt/benchmarks/smear_lowest_bit.py) and the C version
(results/c/smear_lowest_bit.c); this choice is deliberate and is part of a
contract. Had zero been chosen, the two-instruction trick would have ceased to
be equivalent to the specification, the floor sweep would have targeted a
different question, and the compiler row would have pointed to a different
function. Therefore, any benchmark with the case of an empty scan received this
treatment: the output value generated by the trick is written the same way in
both languages.

Counting includes every instruction in the function body except for ret, as
implemented in scripts/compiler_gap.py and tested in
tests/test_compiler_gap.py. Benchmarks are compiled to leaf functions without a
prologue so that the body was clearly defined and prevented drifting due to
manual interpretation.

There are two compiler columns per compiler. The x86-64 column is the baseline.
The -march=x86-64-v3 column is also included since this feature level enables
BMI1, BMI2, and POPCNT, and allows some tricks to be realized in a single
instruction (blsi for isolate-rightmost-bit, popcnt for population count, rorx
for a rotate). This is a hardware consideration rather than a code generation
issue, so two columns are shown.

Superopt's figure is IR instructions with free constants, according to the
project definition of optimality. A superopt tally shows up in the table only
when verified according to the project tier requirements; the tier ladder below
precisely describes the meaning for every row.

Versions: Local GCC is gcc (MinGW-W64 x86_64-ucrt-posix-seh, built by Brecht
Sanders, r8) 13.2.0; Clang is 22.1.0, downloaded from Compiler Explorer with
compiler id cclang2210. All 28 Clang snapshots in results/asm are of the same
version, ensuring no intra-column version skew. Local GCC snapshots use the
MinGW/Windows ABI, while Godbolt Clang snapshots use SysV; this affects
register conventions but not instruction counts, hence not affecting the
comparison.

## The tier ladder

The superopt column provides several types of claims, hence the need for a
four-tier labeling scheme, the strongest first, with every row having exactly
one label.

Proven. Synthesis identifies a program of length n, and a component-library
floor sweep at 32-bit with free constants exhausts unsat for every library
containing fewer than n operations. Since the Jha component encoding makes sure
that every library component is used exactly once in a program, exhausting
multisets of a certain length exhausts all programs of this length. Excluding
length 1 or less implicates 11 libraries (one per opcode), length 2 or less 77,
and length 3 or less 363. Seven rows are proven: absval, clear_lowest_bit,
isolate_rmb, rotl5, smear_lowest_bit, times_nine, turn_off_trailing_ones.

Best found. Synthesis identifies a program, and both verification layers agree,
but the floor sweep was either not attempted or failed to complete within the
allowed time. This value is an upper bound that is currently best. Four rows:
avg_ceil, avg_floor, isolate_lowest_zero, sign. The floor-frontier section
below describes which sweeps failed and how badly.

Verified upper bound. A hand-built IR program, exhaustively verified against
the Python specification at small widths and fuzzed at 32-bit, without a claim
of minimality. Synthesizing at that size is beyond the measured frontier, so
there is no synthesized program and no floor. Two rows: bswap32 at 9 and flp2
at 12. These two rows lack the SMT layer, which reflects an important
distinction: the SMT proof in this project concerns two IR programs, since
equivalent() encodes both sides as bit-vector formulas and asks Z3 whether
there is an input that separates them. For the proven and best-found rows, two
IR programs are compared (the synthesized one and the IR specification),
allowing a meaningful proof. For bswap32 and flp2, the only artifact is the
hand-built IR program; it matches a naïve Python loop with branches, while the
IR program does not contain any, so there is no second formula for the query.
In this case, exhaustive interpretation at widths sufficient to cover the
entire input space, plus fuzz at 32, are performed. The tests
test_flp2_upper_bound_verified (widths 8 and 16; 32-bit width with 12
instructions; fuzzing 20,000 cases) and test_bswap32_upper_bound_verified (full
input set at width 16; four directed 32-bit vectors; 9 instructions; fuzzing
20,000 cases) provide a guarantee at 8 and 16 bits and strong evidence at 32,
though no proof; hence the label does not represent a proof.

No result. popcount, where the synthesizer did not converge. One row.

Every number in the top three tiers also passes the independent fuzzer, per
policy.

## What the survey found

Fourteen rows fall into four groups, and the group classification offers more
information than the numbers.

### Cases where superopt always wins and the reason of the uniformity

The unambiguous wins share one pattern: a naive loop that scans bit positions,
where the result is a two- or three-instruction identity. There are four cases,
plus the sign case, which is smaller and less confident.

The four canonical cases are clear_lowest_bit, smear_lowest_bit,
turn_off_trailing_ones, and isolate_lowest_zero. Every C source loops over 32
bit positions searching for the first set (or clear) bit and returns a function
of it. GCC retains the loop in all cases (18 instructions for clear_lowest_bit
baseline, 16 for v3; 19 and 17 for smear_lowest_bit; 14 and 12 for
turn_off_trailing_ones; 14 and 15 for isolate_lowest_zero). The v3 column shows
modest directional shifts, suggesting a scheduling variance rather than a
pattern recognition. Clang tends to unroll: 98, 97, 96, and 96 instructions,
mov/test/jne pattern per bit position, concluding with the operation the loop
targeted. Neither of these approaches is wrong; both of these reflect the
situation where the optimizer lacks a rewriting rule, and the options are to
retain a loop or unroll due to the known trip count.

Superopt proves 2 for the first three: x & (x-1), x | (x-1), x & (x+1). Each
results from a two-operation library with one free constant
(test_clear_lowest_bit_synthesizes, test_smear_lowest_bit_synthesizes,
test_turn_off_trailing_ones_synthesizes), each proved equivalent to its IR
specification for all 32-bit inputs and fuzzed against the Python benchmark,
and each accompanied with an 11-library floor sweep that excludes all
one-instruction programs (test_clear_lowest_bit_proven_at_2,
test_smear_lowest_bit_proven_at_2, test_turn_off_trailing_ones_proven_at_2).
Isolate_lowest_zero achieves 3 (the form ~x & (x+1)), similarly verified, but
is listed as best found rather than proven due to an unfulfilled 77-library
sweep. The rest of the discussion below explains this point in more detail.

The size of these gaps is the core finding of the survey. Against GCC, the
gaps are 18 versus 2, 19 versus 2, 14 versus 2, and 14 versus 3. Against Clang,
the gaps are 98 versus 2, 97 versus 2, 96 versus 2, and 96 versus 3,
corresponding to a factor of 49 on the first row. The four rows recommended for
Stage B (strongest first) are clear_lowest_bit, smear_lowest_bit,
turn_off_trailing_ones, isolate_lowest_zero. All four correspond to entries in
Hacker's Delight that a practitioner would plausibly implement, and all four
pass portability criteria since the discovered programs use standard
AND/OR/ADD/SUB/NOT operations without IR-over-width shift semantics.

Sign is the quieter fifth win. GCC generates six instructions at both feature
levels, a xor/test/je/mov/sar/or sequence that keeps one branch for the zero
case. Clang manages to produce five with a different approach:
test/sets/setg/sub/movsx. Superopt's program uses four instructions,
ashr(x, 31) | lshr(-x, 31), synthesized from a four-operation library with two
free constants and verified in both directions. However, four is best found
rather than proven: a 363-library sweep necessary to exclude three-instruction
solutions exhausted the budget. Hence, the prudent reading of this row is that
superopt discovered a solution one or two instructions shorter than either
compiler, but it cannot yet prove that a shorter solution does not exist.

### Cases where instruction-set advantages show up

There are two rows where the compilers clearly win for the same reason: the
presence of an x86 instruction not represented in the IR.

Rotl5 is a good example. The naïve source (x << 5) | (x >> 27) is recognized as
a rotate by both compilers. Baseline gives two instructions (mov plus rol). At
-march=x86-64-v3 both compilers generate one instruction, using the BMI2 rorx
to rotate by 27 in the opposite direction. Superopt asserts a minimum of three
(test_rotl5_synthesizes and test_rotl5_proven_at_3), supported by a 77-library
sweep, executed in 20.7 seconds and marked slow. While the proof is correct,
the compilers win because "optimal" in this project is defined relative to the
project's instruction set, which lacks a rotate instruction. This reflects the
purpose of the row: a proven optimal result that is surpassed by the real
compiler, with a concise explanation. Introduction of a rotate opcode would fix
the gap, but this work deliberately avoids such change to stay within the
defined scope.

bswap32 communicates the same principle with greater force. The naïve C code
constructs four bytes and a corresponding reassembly, and both compilers
recognize it as bswap (two instructions with mov). The IR program needs nine
instructions, and nine is a verified upper bound rather than a proven minimum,
because synthesis at nine components is beyond the frontier. Hence, the row
represents two versus nine with no minimality claim on either side; the
important message is that idiom recognition for byte-swapping is present in
both compilers, unlike the bit-scan idioms discussed above, where such
recognition seems to be lacking.

### The near-tie

flp2, rounding down to the nearest power of two, is in the intermediate
position. GCC preserves the naïve top-down scan with 13 instructions baseline
and 14 at v3. The verified upper bound from superopt is 12, achieved by a
smear-then-subtract chain: five shift-or pairs followed by a shift and a
subtract. Hence, the IR program is one instruction shorter than GCC's, but this
resembles a win rather than is, since 12 is an upper bound rather than
demonstrated minimum; 13 corresponds to a scheduled loop rather than a
straight-line sequence, so the counts do not represent the same objects. Clang
again shows as an outlier, reaching 93 by unrolling the 32-iteration scan in
the same way as the four bit-scan benchmarks. The important observation here is
that neither compiler is able to synthesize either the SWAR smear or the
31 − clz(x) formulation from the naïve scan; GCC's output is close enough to
the hand-built IR chain that one would not try a filing.

## Reading three rows closely

### isolate_rmb

Neither compiler recognizes x & -x from the naïve loop. GCC preserves the loop:
a 14-instruction scan looping over bit positions to find the first set bit.
Baseline and v3 builds give 14 instructions, though they do not represent the
same sequence: baseline uses a shift of sall %cl, whereas v3 replaces this with
the BMI2 shlx, redistributing the newer instructions within the same loop
rather than collapsing it to blsi. Clang, conversely, fully unrolls to 97
instructions, mov/test/jne pattern per bit position. Superopt gives 2,
implementing neg followed by and, i.e., x & -x. The length-2 optimum is
provided by the Phase 3 milestone
test_isolate_rmb_rediscovers_two_instruction_trick, while the length-1 floor
follows from test_no_single_instruction_program_matches_isolate_rmb (for both
8-bit and constant-free contexts). Now the
test_no_isolate_rmb_program_of_length_one_or_less carries the floor at 32-bit
with free constants, sweeping every one-op component library and producing
unsatisfiability, which is the component exhaustion argument used in the absval
row. This floor is stronger than the Phase 3 enumeration because it includes
constants and works at the full width.

### absval

This case produces a tie. Both GCC and Clang employ a branchless approach and
converge on 3 instructions, and the superopt's proven minimum is also 3. Both
compilers use the same pattern: mov, neg, followed by conditional moves on the
sign flag (cmovs), invariant across base and v3 for both. They do not use the
sar/xor/sub variant.

Superopt identifies a distinct 3-instruction program, constant-free, with a
wiring x arithmetically shifted by x itself (ashr(x, x)), followed by xoring
with a register, and a subtract: r1 = r1 - r0. The first instruction is the
key: an arithmetic shift by a variable amount (x) produces a sign mask that,
after splitting based on the value of x, is zero for x in [0, 31], and zero for
x of 32 and up with over-width semantics, while negative x produces all-ones
due to the saturation behavior. This corresponds to the classical
(x ^ mask) - mask absolute value, achieved without naming the constant 31.

An important caveat must be stressed. The saturating over-width shift is the
IR's semantics, corresponding to Z3's bvashr; x86's sar masks the shift amount
modulo 32. Therefore, the variant is correct within the project's IR but
non-portable to x86. The optimality claim is scoped to the project's
instruction set, consistent with the CLAUDE.md definition of optimality.
test_synthesizes_branchless_absval_at_32_bit confirms the 3-instruction program
for all 32-bit inputs, and test_no_absval_program_of_length_two_or_less
exhausts all one- and two-op libraries, returning unsat for all of them, hence
proving 3 as the floor.

### popcount

This row is the most informative one: superopt has no converged result, while
the compilers distribute differently. GCC baseline preserves the loop with a
compact implementation of the 32-iteration shift-mask-add, giving 11
instructions. It does not pursue a SWAR-based popcount or the explicit popcnt
instruction. GCC v3 tries to vectorize (25 AVX2 instructions, broadcasting x
across a vector, shifting each lane by varying amounts, masking, and reducing).
Clang baseline unrolls to a 79-instruction bt/adc carry-chain, scanning each
bit and accumulating using the carry flag. Clang v3 goes for a tight AVX2
solution with 24 instructions. Thus, even with POPCNT available in the ISA,
neither compiler recognizes the idiom from the naïve loop.

Superopt gives no converged result in this case; the complete SWAR-based
popcount is still at the frontier of the component synthesizer, described in
the Phase 4b DECISION_LOG: per-round synthesis costs go up due to accumulation
of counterexamples, and the loop does not finish. The two popcount generations
stay in the "slow" category, deselected by default, reflecting practical
difficulty rather than absence of solution.

In summary, fourteen benchmarks reveal four primary groups of outcomes, and the
group membership gives more information than precise numeric values.

## Sidebar: folklore min trick as wrong

The problem is not in tabular form, because the IR cannot represent it as such,
and that is key to the argument.

The folkloric min trick is given by the formula
y + ((x - y) & ((x - y) >> 31)). Interpreted as: calculate the difference,
determine the sign mask of the difference, and then add the difference or
nothing. That takes four operations, no branches, and is wrong. Namely, in case
the true difference does not fit in a signed 32-bit value, x - y overflows, the
sign mask is computed according to the signed value wrapping around, and
selection is in the wrong direction.

The test test_folklore_min_trick_is_wrong from tests/test_survey.py illustrates
this issue. It creates a four-operation IR program, fuzzes it against a Python
implementation of the signed min operation, and asserts the existence of
divergence after 100,000 attempts. The explicit counterexample is given by
x = 0x80000000 (INT_MIN), y = 1, folklore min gives 1, whereas the true min is
INT_MIN. Since INT_MIN - 1 wraps to 0x7FFFFFFF, which is viewed as positive,
the sign mask becomes zero, and the formula reduces to just y.

The verification story is crucial to this argument, because it involves an
admission. A better thing to do was to use equivalent(), because the SMT
counterexample is a proof of the program's incorrectness, while fuzzing gives
only the witness. However, that is not possible in this case for the reasons of
scope, not due to any deficiency: the IR does not have any comparison
operations or branches, so there is no IR program that can play the role of the
converse in the equivalence query. And the signed minimum exists only in the
Python code form. Thus, the SMT layer, which would usually capture
folklore-related bugs missed by sampling, cannot be used in a situation where
the folklore is most likely to be wrong. What saved the day here was the second
layer: an independent fuzzer that does not require IR for the specification.

Two observations follow, both not flattering.

First, the discipline of verification came through: the fact that the proof has
two layers means that a bug will surface even in case one of the layers is not
working.

Second, the scope limitation of the IR is not trivial: it allows the convenient
equivalence query, but comes at the expense of inability to pose certain
specifications to the SMT layer.

## The floor certification frontier

As stated earlier, the framework described above has a soft boundary. A proven
row requires a floor analysis, and the process of full certification
demonstrates strong dependence on specification in unexpected ways.

Certifiable outcomes and their approximate durations:

- isolate_rmb of length one or less, across 11 libraries, seconds in the
  default suite (test_no_isolate_rmb_program_of_length_one_or_less).
- clear_lowest_bit, smear_lowest_bit, and turn_off_trailing_ones of length one
  or less, across 11 libraries each, seconds in the default suite.
- absval of length two or less, across 77 libraries, in the default suite
  (test_no_absval_program_of_length_two_or_less).
- rotl5 of length two or less, across 77 libraries, 20.7 seconds, marked as
  slow and deselected (test_rotl5_proven_at_3).
- times_nine evaluated against each non-multiply single-op library, across 10
  libraries, in test_length_optimal_times_nine_is_the_multiply.
- cost sweep weight 1 stage, i.e. the libraries in _libraries_by_cost, before
  the multiply, within test_cost_optimal_times_nine_is_shift_add.

Not certifiable within the allotted budget:

- isolate_lowest_zero of length two or less (same 77 libraries as absval and
  rotl5) was running for hours.
- sign, avg_floor, and avg_ceil of length three or less (363 libraries each)
  were still running after 35 minutes.

The four floor tests above were deleted in commit 30c9cb3. There should be an
explanation rather than a deletion, because a test that never once succeeded
does not deserve to be called "proven," and leaving it as a slow entry would
mean asserting something that was never seen passing within the repository.
Deleting the tests and downgrading the four rows to best found matches the
empirical knowledge.

Before accepting this decision, two alternative strategies were considered and
dismissed.

First, pre-seeding each CEGIS iteration with 16 random examples of
input/output, hoping to narrow down the search space of the CEGIS procedure and
speed up refutation of the incorrect libraries. It turned out to be
detrimental: each finite synthesis iteration had to solve for 16 examples now,
and the cost per iteration increased enough for the sweep not to finish even
after 10 minutes at the stage marked as "slow" before.

Second, omitting CEGIS completely and posing to Z3 the following
doubly-quantified question: exist a wiring and a constant assignment such that
for all inputs the program satisfies the specification, negated for
contradiction. It defeats the purpose of CEGIS and immediately runs into
troubles: Z3 returned unknown after a 60-second timeout on some library pairs
with ADD transitions, producing an uninterrupted stream of UNKNOWN responses.
The script used is forall_floor.py. UNKNOWN is not a floor, so this road leads
nowhere.

The primary observation to report is the spread itself. Sweeps with exactly 77
libraries produce strikingly different outcomes: absval completes in the
default suite, rotl5 takes 20.7 seconds, and isolate_lowest_zero fails to
finish after hours. Same library counts, same code paths, same width, same
budget allotment produces different outcomes. Therefore, the cost of floor
certification depends on the specification and not on the size of the search
space, thus the tier of the row cannot be computed in advance.

Hypothesis (not verified yet): the time consumption is driven by near-solution
candidates. It is cheap to refute a library when it is eliminated on the first
example, but it is expensive to refute a library that satisfies many example
sets during several iterations of synthesis-verify-refine before the ultimate
unsat verdict. Libraries built from ADD and AND family operations, with four
free constants (the sweep helper gives a library with size k and 2k constants),
have plenty of freedom to remain consistent with finite examples, so that
synthesis lasts for quite a number of rounds before the final unsat. If this is
true, then the specification which behavior is compatible with additive library
constructions is relatively expensive, while isolate_lowest_zero's ~x & (x+1)
falls into the expensive category, and rotl5's shift-or form is outside.
Testing this hypothesis requires the instrumentation of number of rounds per
library, which has not been done.

## Limits

The results are based on a single local setup: gcc MinGW 13.2.0, while the
clang version 22.1.0 is given as checked-in snapshots from Compiler Explorer
rather than being run locally. This means that gcc columns regenerate on each
run of the script, while clang columns are static files, and the clang value
changes only on fetching. MSVC or other non-x86 target versions are not
included.

There are fourteen benchmarks in total, representative sample, but not a
complete suite. The benchmarks are selected mainly from Warren's Hacker's
Delight, which introduces the bias towards functions having a short branchless
form. This is the right kind of bias to ask the compiler if it finds the known
trick, but not a proper one to estimate how often this kind of concern arises
in practice.

Out of fourteen rows, seven rows have a proven floor, four are best found with
no completed floor, two have verified upper bound without minimality claims and
without an SMT layer, and one row has no result at all. The boldface in the
last column in the table shows this distinction, and the tier ladder above
illustrates the advantages of each label.

The whole table is based on instruction counts, not latency: a three operation
sequence with a slow multiply can be beaten by a longer sequence built from
cheap shifts. The alternative view is described in results/cost_model.md: the
compiler columns keep counting instructions, and the cost document presents the
opposite comparison. The times_nine row is the point of divergence between the
two.

The first of these is now filed: the bit-scan loops are llvm/llvm-project
issue #212908 (<https://github.com/llvm/llvm-project/issues/212908>). The GCC
twin is pending an account. A gap in the
table does not mean a compiler bug in itself. Reporting the row requires more
than a numeric value: replication of the result on the current trunk versions
of gcc and clang, portability check to make sure the shorter sequence remains
valid on real x86 (the absval ashr(x,x) construction fails this criterion),
cross-check on other trackers, and argument about why the naive form would
appear in real code. This is what makes the row suitable for Stage B reporting,
with bit-scan rows making its input queue.
